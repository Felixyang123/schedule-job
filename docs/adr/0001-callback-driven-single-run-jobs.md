# 0001-callback-driven-single-run-jobs

为了保障“单次任务 (Single-Run Job)”在分布式环境下的精确一次执行（At-Least-Once / Exactly-Once 执行成功），我们决定采用基于**异步 RPC 执行结果回调**的状态机变更机制，而非调度瞬间立即将任务置为终态。

## 上下文与痛点
单次任务通常用于关键业务场景（如一次性数据订正、特定时刻的报表初始化）。若在调度器（Admin）刚发出 RPC 请求的瞬间（方案 A）就立即将任务置为终态并禁用：
* 若执行节点（Worker）在接收请求前崩溃，或网络连接发生闪断，该任务将永久失效且不会重试，导致业务逻辑静默失败。

## 决策决定
1. **单次任务从延迟队列出队后，不立即自动加回 `DelayQueue`**。
2. **等待异步执行结果**：执行器完成任务执行后，向调度中心通过 Netty 发送成功的 `ScheduleJobResponse`。
3. **基于成功回调禁用任务**：
   - 调度中心接收到成功响应后，在数据库更新 `ScheduleRec` 为 `SUCCESS` 的同时，检测该记录所属的 `Job.type` 是否为 `ONCE`。
   - 若是，则在同一个数据库/应用事务中，将 `Job.status` 更改为 `UNABLE (0)`。
4. **失败处理**：若返回失败响应或调用超时（`onFailure`），该 Job 维持原运行状态（不流转到终态），允许人工重试或由集群容错机制重新触发调度。

## 考量与权衡
* **优点**：极高地保障了业务可靠性，确保单次任务“真正执行成功”才进入禁用的终态。
* **代价**：增加了调度回调逻辑的复杂性，调度中心更新 `ScheduleRec` 时需要联动查询并更新 `Job` 的状态。
